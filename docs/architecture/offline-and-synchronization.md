# Offline-First Operation and Synchronization

**[Proposed]** protocol, see [ADR-0009](../decisions/ADR-0009-offline-synchronization.md). Covers R-OFF-01..06. This is the canonical document for the sync protocol and conflict rules.

## 1. Goals and non-goals

Goals: full read access to synced data offline, offline create/edit/delete of core entities, durable queued changes, automatic and manual sync, multi-device convergence, **no silent loss of financial data**, and sync that is independent of the WebSocket.

Non-goals: peer-to-peer sync, CRDTs, offline authentication of a never-logged-in device, offline attachment upload (v1, see [OQ-09](../planning/open-questions.md#oq-09-offline-attachment-uploads)), offline admin functions, offline exchange-rate fetching.

## 2. Overview

```
 Client (IndexedDB / Dexie)                                   Server (PostgreSQL)
 ┌───────────────────────────┐   push: batch of mutations   ┌────────────────────────────────┐
 │ entity tables (replica)   │ ───────────────────────────► │ command handlers (same as REST)│
 │ outbox (pending mutations)│ ◄─────────────────────────── │ idempotency_records            │
 │ conflicts                 │   per-mutation results       │ entity tables (+version)       │
 │ meta: cursor, deviceId    │                              │ change_log (userId, entity, seq)│
 └───────────────────────────┘   pull: changes since cursor │ user_sync_state (lastSeq)      │
            ▲                 ◄─────────────────────────────┤                                │
            │  Socket.IO "sync:poke {seq}" (hint only)      └────────────────────────────────┘
```

- **Push** sends mutations (commands), not row diffs. The server runs real domain validation.
- **Pull** returns the latest **state** of entities changed since the cursor (state-based, not an operation log).
- The **WebSocket is only a hint** that new changes exist. Without it, the client polls (every 60 s while visible, plus on focus, on `online`, after push, and on manual "sync now").

## 4. Identifiers and versions

- All synced entity IDs are **UUIDv7**, generated by the client for offline creates (time-ordered, which is index friendly). The server validates the format. If an ID already exists **for the same user** and the mutation is a create, the request is treated as idempotent replay or conflict (see below). If it exists for **another user**, the server returns a generic `ID_CONFLICT` without revealing anything. The client regenerates and retries (practically never happens).
- Every synced row has `version INT NOT NULL DEFAULT 1`, incremented by the server on each update. Clients never set versions.
- `mutationId` (UUIDv7 per mutation) is the idempotency key.

## 5. Server-side change tracking

```sql
user_sync_state(user_id PK, last_seq BIGINT NOT NULL DEFAULT 0)

change_log(
  user_id UUID, entity_type TEXT, entity_id UUID,
  seq BIGINT NOT NULL, op TEXT CHECK (op IN ('UPSERT','DELETE')), version INT,
  changed_at TIMESTAMPTZ,
  PRIMARY KEY (user_id, entity_type, entity_id))
INDEX change_log(user_id, seq)
```

Within the **same DB transaction** as every write to a synced entity:
1. `UPDATE user_sync_state SET last_seq = last_seq + 1 WHERE user_id = $1 RETURNING last_seq` (row lock that serializes this user's writers).
2. `INSERT INTO change_log … ON CONFLICT (user_id, entity_type, entity_id) DO UPDATE SET seq = EXCLUDED.seq, op = …, version = …`.

Why a per-user counter instead of a global `bigserial`: with a sequence, transaction A can take seq 10, transaction B take seq 11 and commit first, and a client pulling in between would advance its cursor to 11 and **never see 10**. The per-user row lock forces a user's writes to commit in seq order, so a cursor can never skip a change. Contention is per user only, which is negligible at this scale.

The change log keeps **one row per entity** (the latest change). It is a compacted index, not a history. Deletions leave a **tombstone** row (`op = DELETE`, no data). Tombstones older than **`SYNC_TOMBSTONE_RETENTION_DAYS` (default 90)** are purged daily. The purge records `user_sync_state.min_valid_cursor`.

All writers (REST handlers, sync handlers, jobs, import, base currency change) go through a single `ChangeTracker.record(tx, userId, entityType, entityId, op, version)` helper. A test asserts that every synced entity's write paths call it.

## 6. Pull protocol

`GET /api/v1/sync/pull?cursor=<seq>&limit=500`

```json
{
  "changes": [
    { "entityType": "transaction", "id": "0193…", "op": "UPSERT", "version": 4, "seq": 1201, "data": { …DTO… } },
    { "entityType": "category", "id": "0192…", "op": "DELETE", "seq": 1202 }
  ],
  "cursor": 1202,
  "hasMore": false,
  "serverTime": "2026-11-18T10:00:00Z"
}
```
- The server selects `change_log WHERE user_id = $u AND seq > $cursor ORDER BY seq LIMIT $limit`, then loads the current entity DTOs in bulk per type. If an entity was changed again between the two reads, the returned data is newer, which is fine (state-based). The client keeps `max(seq)`.
- `cursor = 0` means **bootstrap**: the same query returns every live entity (and recent tombstones). The client paginates until `hasMore = false`, then marks the replica as complete.
- If `cursor < min_valid_cursor`, the response is `410 SYNC_RESYNC_REQUIRED`. The client keeps its outbox, wipes replica tables, and re-bootstraps from 0, then re-pushes the outbox.
- Responses are DTOs from `@monevo/contracts` (the same shapes as the REST API).

## 7. Push protocol

`POST /api/v1/sync/push`

```json
{
  "deviceId": "…",
  "mutations": [
    { "mutationId": "0193…", "entityType": "transaction", "op": "create", "entityId": "0193…",
      "payload": { …create DTO… }, "clientChangedAt": "2026-11-18T08:15:00Z" },
    { "mutationId": "0193…", "entityType": "transaction", "op": "update", "entityId": "0192…",
      "baseVersion": 3, "changes": { "description": "Lidl", "amount": "54.20" },
      "baseValues": { "description": "Lidl Sp. z o.o.", "amount": "45.20" } }
  ]
}
```
- At most 100 mutations per request. They are processed **in order**, **each in its own DB transaction** (one failure doesn't roll back unrelated, already-applied mutations; a dependent later mutation can still fail with `REFERENCE_MISSING`).
- Per-mutation result:
  ```json
  { "mutationId": "…", "status": "APPLIED" | "DUPLICATE" | "CONFLICT" | "REJECTED",
    "entity": { …current server DTO… }, "error": { "code": "…", "details": … } }
  ```
- **Idempotency:** `idempotency_records(user_id, key, request_hash, response, created_at)` holds `mutationId` → stored result, retained 30 days. A replayed mutation returns the stored result with status `DUPLICATE`. If the same key arrives with a different payload hash, it returns `REJECTED IDEMPOTENCY_KEY_REUSED`.
- Push and pull are independent. After a push the client always pulls. Applied mutations also come back via pull (the client reconciles them by ID and version).

## 8. Field-level three-way merge

For `update`, the client sends `baseVersion`, `changes` (new values of changed fields only), and `baseValues` (the values of those fields in the client's base snapshot). The server:

1. If `entity.version == baseVersion` → apply.
2. Else, for each changed field `f`: if `current[f] == baseValues[f]`, nobody else changed `f`, so it is safe. Otherwise `f` is **contested**.
3. If no field is contested → apply all (auto-merge). The result is `APPLIED` with the merged entity.
4. If fields are contested → apply the entity-specific **merge policy**:
   - **Financial field groups → CONFLICT** (nothing is applied, and the server returns its current entity).
   - **Non-financial fields → server-side last-writer-wins by arrival** (the client's value is applied). The result is `APPLIED` with `"merged": ["name"]` so the UI can show a subtle notice.

Field groups are compared as a unit, so partial merges can never produce a nonsensical combination:

| Entity | Financial groups (conflict) | Non-financial (LWW) |
|---|---|---|
| Transaction | `{type, postings.* (accounts, amounts, currencies, rates)}`, `{occurredOn, occurredAt}`, `{categoryId}` | description, notes, customFields (per field) |
| Account | `{currency, openingBalance, openingDate}` | name, kind, icon, color, sortOrder, includeInNetWorthWidget, archived flag (archive wins, see matrix) |
| Category | `{type, parentId}` | name, icon, color, sortOrder |
| ScheduledTransaction | `{type, accounts, amount, currency, transfer amounts}`, `{recurrence, startDate, endDate, maxOccurrences}`, `{mode}` | name, description, notes, reminderDaysBefore, isBill, categoryId (*) |
| Budget | `{limitMode, limitAmount, auto config, rollover}`, `{period config}`, `{categoryIds, accountIds}` | name, icon, color, alerts |
| SavingsGoal | `{targetAmount, targetCurrency, source}`, `{deadline}` | name, icon, color, status |
| UserSettings | `{baseCurrency}` (never via sync; separate online operation), `{timeZone}` | locale, theme, weekStart, formats, reminderTime, list columns |
| DashboardLayout, AlertRule, Template, CustomFieldDefinition | n/a | whole-entity LWW |

(*) A category is not financial for schedules because no money has moved yet.

The rule "LWW is never used for financial fields" (R-OFF-06) is enforced by this table, which lives in each module's `*.sync.ts` adapter and is unit-tested.

## 9. Conflict matrix

| Client mutation | Server state | Result |
|---|---|---|
| create | ID not present | APPLIED |
| create | same ID exists, same user, same mutationId | DUPLICATE (from idempotency record) |
| create | same ID exists, same user, different mutation | treated as `update` against version 1 (rare: double-submit after record loss) |
| update | version matches | APPLIED |
| update | version differs, no contested fields | APPLIED (auto-merged) |
| update | contested non-financial only | APPLIED (LWW, notice) |
| update | contested financial group | **CONFLICT** → user resolves |
| update | entity deleted on server | **CONFLICT `DELETED_ON_SERVER`** → user chooses "discard my edit" or "recreate with my version" (recreate = new create with a new ID, history notes "restored from conflict") |
| delete | version matches, or the server changed only non-financial fields | APPLIED |
| delete | server changed financial fields since baseVersion | **CONFLICT `MODIFIED_ON_SERVER`** → user confirms delete of the current version, or keeps it |
| delete | already deleted | APPLIED (idempotent) |
| any | referenced entity missing (category, account deleted) | **REJECTED `REFERENCE_MISSING`** → the conflict UI lets the user pick a replacement and retry |
| any | invariant violated (archived account, transfer same account, pot would go negative, type/category mismatch) | **REJECTED** with a validation code → the user edits and retries, or discards |
| occurrence confirm | already COMPLETED | `DUPLICATE`-like result `ALREADY_COMPLETED` with the existing transactionId. If the client's amounts differ → notice with a link to compare. No second transaction is created. |
| occurrence skip | already COMPLETED | REJECTED `OCCURRENCE_COMPLETED` |
| pot allocation create | any | APPLIED (commutative). If it would make the pot negative → REJECTED `POT_INSUFFICIENT` |
| account archive vs. new transaction from another device | archived first | transaction REJECTED `ACCOUNT_ARCHIVED` → user may unarchive or move the transaction |

**No silent loss:** a CONFLICT or REJECTED mutation is never dropped automatically. It moves from the outbox to the client's `conflicts` table along with the server's entity and stays there until the user resolves or discards it explicitly.

## 10. Client design

### Dexie schema (sketch)
```
meta:          key → value (cursor, deviceId, bootstrapComplete, lastSyncAt, schemaVersion, userId)
<entity>:      id, …DTO fields…, _version, _base (last server snapshot for pending rows), _pending (bool)
outbox:        ++seq, mutationId, entityType, op, entityId, payload/changes/baseValues, baseVersion,
               createdAt, attempts, lastError, state: queued|inflight
conflicts:     mutationId, mutation, serverEntity, error, createdAt
```
- The local DB is **per user** (database name `monevo-<userIdHash>`) and is wiped on logout (with a warning if the outbox is not empty). Logging out with pending changes requires explicit confirmation.

### Optimistic writes
A local write performs, in one Dexie transaction: update the entity row (`_pending = true`, `_base` captured on the first pending change if absent) and append an outbox entry. Consecutive updates to the same entity while still queued (not in flight) are **coalesced** into one mutation (same baseVersion and baseValues, merged changes). Create followed by update coalesces into create. Create followed by delete removes both.

### Applying pulled changes
For each change: if the local row has no pending mutations, overwrite it (or delete it on tombstone). If it is pending, update `_base` to the server data and version, and keep the local optimistic values visible. The push result decides the outcome.

### Push loop
- Triggered by an outbox write (debounced 1 s), `online`, a socket poke, focus, an interval, or manual action.
- Sends FIFO batches. Results: APPLIED/DUPLICATE → remove from outbox, write the returned entity as base, clear `_pending` if no more queued mutations for it. CONFLICT/REJECTED → move to `conflicts`, revert the local row to the server entity, and show a badge.
- Network or 5xx errors → exponential backoff with jitter (1 s → 2 s → … max 5 min). Order is preserved and the batch is retried as is (idempotent).
- 401 → stop, prompt re-login. The outbox is preserved (it is keyed to userId, and a different user cannot log in to this replica without wiping).
- Multiple tabs: only one tab runs the sync loop (Web Locks API `navigator.locks.request('monevo-sync')`). Other tabs observe Dexie live queries.

### Calculations offline
Balances, budgets progress, calendar, forecast, and simple dashboard widgets are computed on the client from the replica using `@monevo/domain` (the same code as the server). Heavy reports show the last cached server result with a "data as of …" label when offline.

## 11. Realtime (Socket.IO)

- Path: **`/api/v1/realtime`** (Socket.IO `path` option). Same origin, authenticated by the session cookie during the handshake (token-based handshakes for native clients are **[Deferred]**). Revalidated every 5 min, and disconnected immediately on session revocation.
- Room per user: `user:<userId>`.
- Server → client events: `sync:poke { seq }`, `notification:new { id }`, `session:revoked { sessionId }`, `system:maintenance { mode }`.
- Client → server: none required (all writes go through REST/sync).
- Single process: the default in-memory adapter. If ever multi-instance: `@socket.io/postgres-adapter` (no Redis needed).

## 12. Testing requirements

- Unit: merge policy per entity (property tests: merge never changes financial fields on contest), outbox coalescing, cursor handling.
- Integration (server): concurrent pushes from two simulated devices, cursor monotonicity under concurrent writers (parallel transactions → no skipped seq), idempotent replay, tombstone purge → 410, every conflict matrix row.
- Client: sync engine against `fake-indexeddb` + mocked API. Offline → online replay.
- E2E (Playwright): two browser contexts. Context A goes offline, edits, B edits the same transaction amount, A comes online → conflict UI → resolve. Offline create of an expense → reconnect → visible on B.

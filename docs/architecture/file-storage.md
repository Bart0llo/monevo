# File Storage and Attachments

**[Accepted]** files outside PostgreSQL behind a storage abstraction (R-ATT-03), see [ADR-0010](../decisions/ADR-0010-file-storage-abstraction.md). **[Proposed]** details. Covers R-ATT-01..05 and R-ADM-03.

## 1. Scope

- Attachments belong **only to transactions** (R-ATT-05). Any file type is accepted, and several files per transaction are allowed.
- Content lives in a storage backend: a local Docker volume or S3-compatible storage. **PostgreSQL holds metadata only.**
- Branding assets (instance logo) are small and stored in `app_settings` as validated PNG/WebP data (max 256 KB), not in attachment storage.
- Uploads require connectivity in v1 ([OQ-09](../planning/open-questions.md#oq-09-offline-attachment-uploads)).

## 2. Storage driver interface

```ts
interface StorageDriver {
  readonly id: 'local' | 's3';
  put(key: string, body: Readable, opts: { contentLength?: number; contentType: string }): Promise<{ size: number }>;
  get(key: string, range?: { start: number; end?: number }): Promise<{ body: Readable; size: number }>;
  head(key: string): Promise<{ size: number } | null>;
  delete(key: string): Promise<void>;          // idempotent: deleting a missing key succeeds
  list(prefix: string): AsyncIterable<{ key: string; size: number; lastModified: Date }>;  // orphan sweep, backups
  probe(): Promise<void>;                      // startup write/read/delete check
}
```

| Driver | Implementation |
|---|---|
| `local` | Files under `STORAGE_LOCAL_PATH` (default `/data/attachments`). Writes go to a temp file in the same volume and are `rename`d into place on success, so partial files are never visible. Directories are created with mode `0700`, files `0600`. |
| `s3` | `@aws-sdk/client-s3` + `@aws-sdk/lib-storage` multipart upload. Configured via `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE` (MinIO, Garage). The bucket must be private; the app never issues public or presigned URLs in v1, and all downloads stream through the app (authorization in one place). |

- The driver is selected by `STORAGE_DRIVER=local|s3` at startup ([configuration.md](../infrastructure/configuration.md)). Changing the driver on an instance with data requires migrating objects. A migration tool (`cli storage-migrate`) is **[Deferred]**; until then the operator copies objects with standard tools (keys are identical for both drivers).
- The driver is an infrastructure component (`storage` module). Only `attachments` and `backups` use it.

## 3. Keys and metadata

**Storage key:** `users/{userId}/attachments/{attachmentId}`. It is generated by the server from two UUIDs. No user-supplied text (filename, extension) ever appears in a key, which rules out path traversal by construction. The local driver additionally resolves the final path and asserts it stays under the storage root.

```
Attachment: id (UUIDv7), userId, transactionId, storageKey (internal, never in DTOs),
            originalFilename (sanitized display name), sizeBytes, declaredMime, detectedMime?,
            sha256, status: PENDING | READY, createdAt
```

- `originalFilename` is sanitized: Unicode NFC, control characters and path separators removed, max 255 bytes, fallback `file`. It is only used for display and in `Content-Disposition` (RFC 6266 `filename*` encoding).
- `detectedMime` comes from magic-byte detection (`file-type`). `null` means unknown (served as `application/octet-stream`).
- `Attachment` metadata is synced (read-only offline). Content is fetched on demand and cached by the service worker (LRU 50 MB) after the user opens it ([offline-and-synchronization.md](offline-and-synchronization.md#3-synced-entities)).

## 4. Upload flow

`POST /api/v1/transactions/:id/attachments` (multipart, one or more `file` parts).

1. Authenticate, check CSRF, rate limit (30/min per user), and verify the transaction belongs to the user (404 otherwise).
2. If the request declares `Content-Length` larger than `MAX_UPLOAD_BYTES` × file count + overhead, reject early with `413 PAYLOAD_TOO_LARGE`.
3. For each file part (busboy, streaming, never buffered whole in memory or on disk outside the storage driver):
   1. **Reserve quota:** in a short DB transaction, `SELECT … FROM users WHERE id = $1 FOR UPDATE`, check `storage_used_bytes + declaredSize ≤ quota` (declared size = `Content-Length` of the part if given, otherwise `MAX_UPLOAD_BYTES`), add the reservation, and insert the `Attachment` row with status `PENDING`. Over quota → `413 QUOTA_EXCEEDED`.
   2. Stream to `driver.put` through a byte counter and SHA-256 hasher. If the counter exceeds `MAX_UPLOAD_BYTES`, abort the stream, delete the partial object, release the reservation, and return `413`.
   3. Sniff the first 4 KB with `file-type` → `detectedMime`.
   4. **Finalize:** in one DB transaction, set status `READY`, the real size, `sha256`, `detectedMime`, adjust `storage_used_bytes` from the reservation to the real size, write the transaction audit entry (`attachments.added`), and record the change log entry.
4. Respond with the attachment DTOs. On any failure after `put`, the object is enqueued in `storage_deletions` and the reservation is released.

Rows stuck in `PENDING` (crash mid-upload) are cleaned by the daily orphan sweep (older than 24 h → delete object if present, release reservation, delete row).

## 5. Quotas

- Per-user quota: `users.storage_quota_bytes` (null = instance default, runtime setting `storage.defaultQuotaBytes` in [configuration.md](../infrastructure/configuration.md#runtime-settings-app_settings)). `0` disables uploads for that user.
- Usage: `users.storage_used_bytes`, maintained transactionally (reservation, finalize, delete). It counts `PENDING` reservations and `READY` sizes. Objects waiting in the deletion grace period are **not** counted (the user has deleted them).
- A daily reconciliation in the orphan sweep recomputes `Σ size_bytes` per user and corrects drift, logging a warning if it finds any.
- The admin sets the default and per-user overrides and sees per-user usage (operational data only, R-ADM-05). The user sees a usage bar in settings (`GET /me/storage`).
- Lowering a quota below current usage blocks new uploads but never deletes files.

## 6. Download and preview

`GET /api/v1/attachments/:id/content[?disposition=inline]`

- Owner-only (404 for others). Streams from the driver with `Content-Length`, `ETag` (sha256), `Cache-Control: private, max-age=0, must-revalidate`, and `Range` support (for large PDFs).
- `Content-Type` is the **detected** MIME if known, otherwise `application/octet-stream`. The declared MIME is never trusted for serving.
- **Inline preview** only when `disposition=inline` is requested **and** `detectedMime` is in the allowlist `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `application/pdf`. Those responses add `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`.
- Everything else is served with `Content-Disposition: attachment`. SVG, HTML, XML, and JavaScript are never served inline, regardless of their content.
- Thumbnails are rendered client-side from the inline image. There is no server-side image processing in v1 (no native image libraries in the image).

## Deletion

Physical deletion is **delayed** so backups stay consistent ([ADR-0011](../decisions/ADR-0011-backup-and-restore.md)).

```
StorageDeletion: id, storageKey, sizeBytes, requestedAt, notBefore, attempts, lastError?, doneAt?
```

1. Deleting an attachment (or a transaction with attachments, or an import rollback) deletes the `Attachment` row and inserts a `storage_deletions` row **in the same DB transaction**, with `notBefore = now + grace period`. The quota is released immediately and the audit entry records `attachments.removed`.
2. The **grace period** is at least the backup interval: `max(7 days, configured backup interval)`. A backup taken before the deletion therefore still finds the object in storage when it copies attachments, and a restore of that backup has all its files.
3. Job `storage.purgeDeleted` (hourly) deletes objects with `notBefore ≤ now`, marks rows done, and retries failures with backoff. Done rows are purged after 30 days.
4. Objects are **immutable**: a key is written once and never overwritten. Together with delayed deletion, this lets backups copy files after the database dump without a global lock (see [backups-and-restoration.md](../infrastructure/backups-and-restoration.md)).
5. **Orphan sweep** (`storage.orphanSweep`, daily): lists objects under `users/` and deletes those with no `Attachment` row and no pending `storage_deletions` row, but only if older than 24 h (protects in-flight uploads). It runs after a restore too.

User deletion (deferred in UI) enqueues all of the user's objects the same way.

## Security

Summary of upload and download controls (R-ATT-04, [security.md](security.md#uploads-and-downloads)):

| Threat | Control |
|---|---|
| Path traversal | Server-generated keys from UUIDs only; resolved-path check in the local driver; filenames never used in paths. |
| Oversized uploads / disk exhaustion | `MAX_UPLOAD_BYTES` enforced while streaming; quota reserved under a row lock before writing; upload rate limit. |
| Stored XSS via uploaded HTML/SVG | Served as `attachment` with the detected (not declared) MIME; inline only for the raster/PDF allowlist with `CSP: sandbox` + `nosniff`. |
| MIME confusion / polyglots | Magic-byte detection; unknown types served as `application/octet-stream`. |
| Unauthorized download | Owner check on every request; no public or presigned URLs; private S3 bucket. |
| IDOR via attachment ID | 404 for foreign IDs; covered by the isolation suite. |
| Malware | Not scanned in v1 (files are only served back to their owner). An optional ClamAV hook is a possible later addition and does not need design changes. |
| Leaking metadata | `storageKey` never appears in DTOs or logs at info level; filenames are not logged. |

## 7. Admin view

`/api/v1/admin/storage`: driver id, endpoint and bucket (no credentials), probe status and last error, total used bytes, number of objects, pending deletions, last orphan sweep result, default quota. See [administration.md](administration.md).

## 8. Testing

- Unit: filename sanitization, MIME allowlist decision, key generation.
- Integration: both drivers (local in a temp dir, S3 against MinIO) via one shared driver contract test suite; upload over the size limit is aborted with no object left; concurrent uploads cannot exceed quota; deletion grace period with an injected clock; orphan sweep keeps in-flight uploads.
- Security: downloading another user's attachment → 404; an uploaded `.html` file is served as `attachment`; an SVG with `disposition=inline` is still served as `attachment`.

# Database Architecture

**[Accepted]** PostgreSQL + Prisma ([ADR-0003](../decisions/ADR-0003-postgresql-and-prisma.md)). **[Proposed]** conventions. Logical schema: [data-model.md](../data/data-model.md). Relationships: [entity-relationships.md](../data/entity-relationships.md).

## 1. Conventions

| Aspect | Convention |
|---|---|
| Naming | Tables `snake_case` plural. Columns `snake_case`. Prisma models `PascalCase` singular with `@@map`/`@map`. |
| Primary keys | `id UUID` (UUIDv7, generated by the app or the client; no DB default needed, though `gen_random_uuid()` is a fallback for server-only tables). |
| Ownership | `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE` on every owned table. |
| Timestamps | `created_at`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. `updated_at` is maintained by Prisma `@updatedAt`. |
| Calendar dates | `DATE` for LocalDates (`occurred_on`, `start_date`, `rate_date`). |
| Money | `NUMERIC(19,4)`. Rates `NUMERIC(24,12)`. See [multi-currency.md](../architecture/multi-currency.md). |
| Currency | `CHAR(3)` FK → `currencies(code)`. |
| Enums | PostgreSQL enums via Prisma `enum` for stable sets (transaction type). `TEXT + CHECK` for sets expected to grow (notification type, insight type, widget type), which avoids enum migration pain. |
| JSON | `JSONB` for custom field values, overrides, dashboard layout, report definitions, audit changes, settings. It is always validated by Zod before writing. |
| Versioning | `version INT NOT NULL DEFAULT 1` on synced mutable tables. |
| Text search | `unaccent` + `pg_trgm` extensions. A trigram GIN index on `transactions.description` (lowercased, unaccented) for "contains" search. |
| Case-insensitive email | `citext` extension for `users.email`. |

## 2. Composite ownership foreign keys

Each owned parent table declares `UNIQUE (id, user_id)`. Child tables reference the pair:

```prisma
model Account {
  id     String @id @db.Uuid
  userId String @map("user_id") @db.Uuid
  // …
  @@unique([id, userId])
}

model Posting {
  id        String @id @db.Uuid
  userId    String @map("user_id") @db.Uuid
  accountId String @map("account_id") @db.Uuid
  account   Account @relation(fields: [accountId, userId], references: [id, userId], onDelete: NoAction)
  // …
}
```
Use `NoAction` (checked at the end of the statement) rather than `Restrict` (checked immediately) for child→parent FKs between owned tables. That way a user deletion cascading from `users` through all owned tables succeeds, while deleting a single referenced parent (an account that has postings) is still rejected.
Prisma supports composite relations natively. With this in place a bug that writes a cross-user reference fails at the database. This applies to postings→accounts, postings→transactions, transactions→categories, attachments→transactions, pots→accounts, allocations→pots, goals→pots/accounts, budget_categories→budgets/categories, schedules→accounts/categories, templates→accounts/categories, occurrences→schedules, transactions→schedules.

Nullable composite FKs (for example `category_id` null) use `MATCH SIMPLE` (the default): if `category_id` is null, the constraint is not checked.

## 3. Constraints beyond Prisma's DSL

Prisma migrations are SQL files and can be hand-edited. These are added in raw SQL within the migration that creates the table, and documented in a comment block at the top of `schema.prisma`:

- `CHECK` constraints:
  - `postings.amount <> 0`; `postings.original_amount > 0`; `postings.rate_to_account > 0`; `rate_to_base > 0 OR NULL`.
  - `exchange_rates.rate > 0`; `from_currency <> to_currency`.
  - `accounts.custom_kind_label IS NOT NULL` when `kind = 'CUSTOM'`.
  - `savings_goals`: exactly one of `pot_id`/`account_id` is non-null, matching `source`.
  - `scheduled_transactions.recurrence_interval >= 1`; `end_date >= start_date`.
- **Partial unique indexes:**
  - `transactions (scheduled_transaction_id, occurrence_date) WHERE scheduled_transaction_id IS NOT NULL` (idempotent generation, INV-9).
  - `savings_goals (pot_id) WHERE status IN ('ACTIVE','PAUSED')` and the same for `account_id` (one active goal per source).
  - `exchange_rates`: unique over `(COALESCE(user_id, '00000000-…'), source, COALESCE(provider_id,''), from_currency, to_currency, rate_date)` as an expression index.
- **Constraint triggers (deferred) [Proposed]:** `posting_shape_check`, a `DEFERRABLE INITIALLY DEFERRED` constraint trigger on `postings`/`transactions` that validates INV-4 (posting count and sign per type) at commit. This is defense in depth, since services already enforce it. It is cheap at this scale. The decision on whether to include it is made in Stage 4, with a performance check.
- Category depth trigger (parent must be top-level, same type).

## 4. Indexes (initial set)

| Table | Index | Purpose |
|---|---|---|
| transactions | `(user_id, occurred_on DESC, id DESC)` | list and cursor pagination |
| transactions | `(user_id, category_id, occurred_on)` | category reports and budgets |
| transactions | GIN trigram on `lower(unaccent(description))` | description search |
| postings | `(user_id, account_id)` include `amount` | balances |
| postings | `(transaction_id)` | aggregate loading |
| postings | `(user_id, account_id, base_amount)` partial `WHERE base_amount IS NULL` | missing rates |
| change_log | `(user_id, seq)` | sync pull |
| scheduled_occurrences | unique `(scheduled_transaction_id, occurrence_date)` | idempotency |
| exchange_rates | `(from_currency, to_currency, rate_date DESC)` | resolution |
| notifications | `(user_id, created_at DESC)`, unique `(user_id, dedup_key)` | center, dedup |
| sessions | unique `(token_hash)`, `(user_id)` | auth, listing |
| transaction_audit | `(user_id, transaction_id, at)`, `(user_id, at DESC)` | history views |
| attachments | `(user_id, transaction_id)` | listing |

Expected volume: ≤ 10 users × ≤ 50k transactions over years, which is trivial for PostgreSQL. Indexes target interactive latency (< 50 ms queries), not scale.

## 5. Migrations

- `prisma migrate dev` in development (generates SQL). Review and hand-edit SQL for checks, partial indexes, triggers, and extensions before committing.
- **Forward-only** in production: `prisma migrate deploy` in the container entrypoint before the server starts. Prisma's migration advisory lock prevents concurrent runs.
- Migrations must be **backwards-compatible with the previous app version where cheap** (expand → migrate → contract across releases for renames and drops), so a failed upgrade can roll back the image without restoring the DB. When that is impossible, the release notes require a backup before upgrading (the app also takes an automatic pre-migration backup **[Proposed]**; see [backups-and-restoration.md](../infrastructure/backups-and-restoration.md#pre-upgrade-backup)).
- Data migrations (backfills) are written as SQL in migrations when simple, or as an idempotent one-off job flagged in `app_settings.migrations_done` when complex.
- Seed data in migrations: ISO 4217 `currencies` only. Never user data, never categories.

## 6. Connection management

- Prisma 7 with `@prisma/adapter-pg` (node-postgres pool). Pool size 10 (env `DATABASE_POOL_SIZE`).
- pg-boss uses its own small pool (size 3) against the same database (schema `pgboss`).
- `statement_timeout` 30 s for API connections (set per pool connection), longer for backup and report jobs.

## 7. Data lifecycle

| Data | Retention |
|---|---|
| Financial entities | Until deleted by the user (transactions) or user deletion (cascade) |
| Transaction audit | Same as the owning user. See [OQ-11](../planning/open-questions.md#oq-11-history-retention-for-deleted-transactions) |
| Change log tombstones | 90 days |
| Idempotency records | 30 days |
| Sessions | 30 days after expiry or revocation |
| Notifications | 180 days **[Proposed]** (read ones). Unread are kept |
| Insights | Dismissed ones kept 180 days (prevents re-suggesting) |
| Auth tokens | Purged 7 days after expiry or use |
| pg-boss jobs | pg-boss archive defaults (7 days) |

User deletion (admin) is **[Deferred]** in UI. The schema already supports it via `ON DELETE CASCADE` from `users`, plus storage cleanup via `storage_deletions`.
